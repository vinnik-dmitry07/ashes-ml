# AHSL 1.5: исправления после аудита 1.4

11 сентября 2026. Полный выпуск подготовлен без LLM API. Исходный аудит верно подтвердил воспроизводимость 1.4; основные спорные эффекты дополнительно воспроизведены перед исправлением. Новый пакет прошёл **98 тестов**, конечный обход K12, сквозное демо и целевые мутации проверок.

## Что изменено

| Замечание | Результат 1.5 |
| --- | --- |
| Сравнение §7 | Forward получил тот же индекс подцелей и вложенные конъюнкции. Плоская цель: оба CHECKED при 1 pair; вложенная: оба CHECKED при 3 pair. Заявление о доказанном выигрыше планирования снято. |
| Переименование проходит improve | Стоимость считается на форме со связанными именами фиксированной ширины. main→a даёт нулевую дельту и не проходит improve при равных действиях/fuel. |
| Старый снимок повторяет выпуск | D12 сохраняет весь checkpoint и revision во внешней БД SQLite, отзывает прежнего владельца и сверяет восстановление с актуальной записью. |
| Узкое покрытие фаззера | Старый генератор получает точные счётчики. Добавлен генератор из валидных жизненных циклов с мутациями запросов, типов, подписей и fuel. |
| Нет теста разделения principal | Добавлен прямой AUTHORITY-тест. Удаление guard проверено в отдельной копии и приводит к провалу этого теста. |
| Четыре плана | Пожизненный предел сохранён и прямо указан. Проверены четыре законченных выпуска, затем LIMIT на пятом prepare. |
| Неверный реестр сервисов | Проверка формы и сигнатур происходит до исполнения; ошибочный реестр не вызывает callback и получает структурированный отказ. |

Изменение байтовой оси закреплено новым профилем **SUCCESS_THEN_PARETO_COST_2**. В 1.4 арифметика точно сравнивала сырые байты, как и было определено; здесь исправлен сам выбор прокси-метрики. Ограничение `max_program_bytes` продолжает считать реальные байты исходной программы. Нормализованная форма не объявлена полным каноническим представителем смысловой эквивалентности.

Нормализация учитывает функции, параметры, let/shadowing и общие Python-узлы AST в разных областях видимости. Литералы, похожие на код, остаются данными. Регрессии 1.4 по глубине, сериализации и обходу AST сохранены.

## Что именно защищает восстановление

Живой вход — `DurableSession.handle`. Перед исполнением допущенного запроса сохраняется pending; после — новый полный checkpoint, revision+1 и снятие pending. Ответ возвращается после COMMIT. Старый экземпляр после восстановления теряет право следующего dispatch. Из двух конкурентных восстановлений одной пары только одно получает владение.

`DurableSession.restore` проверяет предъявленные snapshot/anchor относительно текущей БД. `open` берёт актуальный checkpoint, если клиент потерял ответ после уже сохранённого выпуска. Если операция могла исполниться, но фиксация не завершилась, pending даёт PHASE: автоматического повторения нет. Внешние отказы размера, типа и wire-квоты проверяются до pending и не создают новые записи checkpoint.

В демо четыре восстановления старой пары отклонены с STALE. После восстановления текущего состояния повтор admit также получает STALE. Итог: **generation=1, spent=2**, а не несколько выпусков из одной оплаченной пары.

**Это не защита от отката самой БД.** SQLite, файловая система и выбор пути принадлежат доверенному владельцу. Для противника, способного откатить всю БД, потребуется независимый монотонный источник. Нет автоматического восстановления pending или произвольной изоляции Python.

Метод `Session.restore` удалён. `Session.restore_integrity` предназначен для офлайн-проверки исторических снимков и не является правом на возобновление. Это намеренное изменение API, чтобы проверка целостности не выглядела проверкой свежести. Снимки, content IDs и производные ключи 1.5 не смешиваются с 1.4.

Старый фаззер: **2000** сгенерировано; **1024** прошли внешнюю границу, из них **998 SCHEMA**, **26 REFERENCE**, **0 OK**. Ещё **976 BUDGET** остановлены до dispatch.

Новый генератор: **768** запросов, в том числе 135 исходных форм и 633 мутации; **97 OK**, 269 SCHEMA, 92 TYPE, 86 AUTHORITY, 83 FUEL, 27 STALE, 101 REFERENCE, 13 DUPLICATE. Задействованы **7 из 17 кодов ошибок**. Это расширение достигнутых состояний протокола, а не полное покрытие всех его путей.

Проверки выполнены на **Python 3.12.14**. Сообщённое в аудите воспроизведение 1.4 на 3.11.15 не записано как наш тест 1.5 на этой версии. Сохранённые отчёты сверены побайтно с завершённым прогоном отдельной копии исходников.

## Воспроизведение

Из корня распакованного пакета:

```bash
python3 verify.py --expected-manifest 01ada0969532bcc9db11d1f2968b2166ef76aa6866396195cccebc5398733430
python3 demo.py
python3 verify_mutations.py
```

Полная спецификация — `SPEC.md`, ответы по пунктам — `AUDIT-CLOSURE.md`, изменения — `CHANGELOG.md`, фактические результаты — `reports/`.

Предел четырёх планов выбран осознанно для конечного эталона. Общая живость, независимое механизированное доказательство F2, обход с тремя job, бесконечная самоэволюция и качество реальных LLM этим выпуском не установлены. Экспериментальный пакет 0.3 продолжает закреплять своё ядро 1.4; его прошлые результаты не переименованы в результаты 1.5.
