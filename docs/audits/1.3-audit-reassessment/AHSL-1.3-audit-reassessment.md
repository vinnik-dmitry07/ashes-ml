# AHSL 1.3 — пересмотр выводов нового аудита

Дата: 2026-09-07. Вход: `Pasted markdown(2).md`. Это дополнение к оценке выпуска, а не новая версия языка. Нормативные файлы и архив AHSL 1.3 не изменены.

## 1. Вывод

Новый файл содержит несколько последовательных сообщений: первоначальные обвинения, их частичное снятие и последующее воспроизведение атак. Поэтому его нельзя свести ни к «пять атак доказали неформальность», ни к «97% обвинений опровергнуты, система безопасна».

Нужно отдельно устанавливать:

1. **Наблюдение:** произошло ли указанное поведение при данных полномочиях и входах.
2. **Соответствие спецификации:** какое конкретное обязательное утверждение оно нарушает в своей области действия.
3. **Пригодность для задачи:** достаточно ли заявленных гарантий для безопасного цикла эволюции и обучения, даже если реализация точно им соответствует.

Раскрытое ограничение может исключать нарушение спецификации и при этом оставаться блокером для применения. Тест, запускающий доверенный Python-код с прямым доступом к состоянию, не является автоматически атакой агента через ограниченный API. Доставка строки с инструкцией не доказывает фактическое повышение полномочий.

Моя прежняя классификация части изменений как «исправлений дефектов 1.0» была чрезмерной. Наличие отображения состояний, определение рангов и раскрытие ограниченного покрытия действительно нужно учитывать. Для таких пунктов точнее говорить об усилении нового профиля, улучшении измерения или закрытии инженерного пробела. Снятие старого обвинения не требует отменять полезное усиление 1.3.

## 2. Что проверено непосредственно

Проверены локальные исходники 1.0 и 1.3, их спецификации, журналы и тесты. Все три локальных lock-файла исходного дерева 1.0 совпадали с файлами до эксперимента. Сам эксперимент проводился в временной копии.

### Дефект аттестации 1.0 воспроизведён

В `runtime_0_6/evidence.py` заменено только условие `n <= 512` на `n <= 4096`, затем пересчитаны два затронутых внутридеревных lock-файла. Запущен прежний `verify.py`.

| Измерение | Результат |
|---|---|
| Код завершения | 0 |
| Число тестов в итоговом отчёте 1.0 | 83 |
| Failures / errors | 0 / 0 |
| `runtime_profile_unchanged` | true |

Флаг действительно задан литералом и не устанавливает неизменность профиля. Пересоздание манифеста может быть законной операцией сборщика новой версии; дефект здесь в том, что отчёт продолжает утверждать проверенную неизменность старого профиля, не имея отдельного эталона для сравнения.

В 1.3 этого флага нет. Идентификатор профиля и `status=EXECUTABLE_REFERENCE` — классификационные метаданные. Числа тестов, ошибки, список файлов и хеш манифеста вычисляются; классификационный статус сам по себе не является машинным доказательством безопасности.

### Проверка якоря 1.3

В отдельной временной копии 1.3 изменён max_actions корневого контракта с 64 на 63.

| Состояние копии | Результат `verify.py --expected-manifest … --quick` |
|---|---|
| Исходный выпуск | 67 тестов прошли |
| Изменён исходник | Отказ: `Manifest differs: changed, missing, or unlisted source` |
| Изменены исходник и локальный манифест | Отказ: `External manifest anchor mismatch` |

Это проверка при **закреплённом внешнем хеше и доверенном verifier**. Запуск без внешнего якоря устанавливает лишь внутреннюю согласованность дерева. Компрометация самого проверяющего процесса или замена внешнего якоря вместе с артефактом не исключены. Старый архив 1.3 имеет тот же SHA-256 после этой работы.

Скрипт эксперимента и полные результаты приложены в `AHSL-1.3-audit-evidence.zip`. Повторение требует двух деревьев `ahsl-1.0/` и `ahsl-1.3/` в указанном workspace; скрипт не загружает и не исполняет сторонний код из сети.

## 3. Какие возражения к прежним аудитам подтверждаются

| Пункт | Проверка источника | Исправленная оценка |
|---|---|---|
| «Отображения в TLA⁺ вообще нет» | `runtime_0_6/kernel/SPEC.md`, §12: отображение Job/cells и stuttering действительно описано | Утверждение об отсутствии неверно. Описание отображения не равно доказанному refinement и не распространяет старую модель на весь release protocol |
| «Ранг придуман самим обходом» | `SPEC.md` 1.0 задаёт ранг прямого сертификата 0 и правило 1+max для нового вывода | Нормативное правило есть. Его наличие не является механизированным доказательством кода |
| «V* дедуктивно пусто» | §6 утверждает soundness условного вывода; не обещает дополнительные следствия относительно полного решателя | Включение в множество прямо сертифицируемых целей не означает пустоты V*. Вопрос полезности декомпозиции остаётся вопросом стоимости поиска |
| «Все коды Python входят в алфавит step» | INCONSISTENT_SCOPE расположен в initial; граница доверенных входных состояний оговорена отдельно | Нужно проверять конкретную публичную функцию и допустимые входы; перечисления строк ошибок недостаточно |
| «Стабильность сведена к replay» | Документ содержит отдельные определения устойчивости исходов и оговорки о конечном покрытии | Нельзя судить обо всём разделе по одной строке таблицы. В 1.3 эти показатели также разделены |
| «Certificate/Note отсутствуют, значит ложна любая исчерпывающая схема» | Исчерпывающий перечень мог относиться только к названным записям | Классификация зависит от области обещания. В текущем выпуске производственные домены хешей перечислены машинно |

Я не воспроизводил работу всех заявленных 49 агентов и не подтверждаю число 32/33 как измеренную частоту ошибок аудита. В самом файле смешаны ошибочные наблюдения, ограничение области обещания и понижение серьёзности. Из этой неоднородной выборки нельзя оценить вероятность ложности ещё не проверенной атаки.

mtime также не устанавливает изменение семантики: он зависит от копирования, распаковки и записи. Для такого вывода нужны сравнение байтов с закреплённой версией и анализ изменения. Для литерала `runtime_profile_unchanged` выше есть более сильное экспериментальное свидетельство.

## 4. Что это означает для пяти атак и AHSL 1.3

| Сценарий | Текущий ответ 1.3 | Остаточная граница |
|---|---|---|
| Ослабление гарантий родителя | `refines(child,published_parent)` вместе с floor; реально измеряются ограничения, включая перед train | Конечные предикаты G12; произвольные контрактные языки и RAM не реализованы |
| Retain нулевого кандидата | Полный абсолютный успех обязателен в обоих режимах | Непрохождение неухудшения и нулевая способность — разные свойства. Сам тест неухудшения корректно может принять две одинаково плохие системы; для нашего допуска он недостаточен |
| Одна роль исполнения и оценивания | Разные ключи, отдельное Assessment, чтение наблюдения, повторное сопоставление действий программе | Один доверенный Python-процесс; это не изоляция ОС |
| Initializable-инъекция | Нет sysprompt-адаптера; строка не расширяет закрытый алфавит действий или wire API | Защита произвольного LLM-потребителя не доказана; исходная атака доставки текста не равна наблюдению эксфильтрации |
| Отравление выборки кривым отчётом | Полная проверка до used; отказ сохраняется в отдельном журнале | Запрос расходует ограниченную API-квоту; выполненный эпизод остаётся оплаченным |
| Бесплатное наращивание proposals | Ограничения числа планов, размера программы, wire-запроса и журнала | Ограничение ущерба не равно устранению всех DoS-сценариев |
| Summary лжёт, сохраняя ссылку | FACT отображается из проверенного assertion; tokens/features также выводятся заново | Свободный пересказ остаётся недоверенным |
| Родительский результат переобъявляется | Родитель и кандидат реально исполняются в каждом плане, исходы выводятся из привязанных квитанций | Старый исторический результат не заменяет новый измеренный результат; повторное измерение родителя само по себе правильно |

Отсутствие отчёта внутри записи Trial не доказывает отсутствие отчёта во всём журнале. Нужно проверить все места хранения и ссылки между ними. Для воспроизводимости важна цепочка назначения и измерения, а не требование обязательно дублировать одни и те же строки в каждом объекте.

Текущие 67 тестов повторно прошли в чистой копии. Конечный обход 6480 состояний относится только к K12; он не запускался заново в этом пересмотре и не выдаётся за новое доказательство Mission, evaluator или памяти. Эти результаты и ограничения уже зафиксированы в выпуске 1.3.

## 5. Исследовательские рекомендации, которые нельзя переносить буквально

### Pass^k и pass@k не являются дополнениями

Для одной задачи с независимыми попытками и вероятностью успеха p:

\[
\mathrm{pass@}k=1-(1-p)^k,\qquad \mathrm{pass}^{k}=p^k.
\]

Первое — хотя бы один успех, второе — все попытки успешны. Дополнение первого — ни одного успеха. При p=0.8 и k=2 получаем соответственно 0.96 и 0.64; дополнение 0.96 равно 0.04. Это согласуется с исходными определениями [τ-bench](https://arxiv.org/html/2406.12045).

Утверждение, что эти метрики обязательно движутся в противоположные стороны при смене температуры или метода, тоже не универсально. Если p каждой задачи выросло при прочих равных, обе растут. Разное поведение возможно при изменении распределения успешности по задачам и зависимости попыток.

### mG-Pass полезен для диагностики, но не заменяет допуск

Работа [G-Pass@k](https://arxiv.org/html/2412.13147v2) определяет семейство по требуемой доле успешных попыток и интегрированную метрику. Из этого не следует защита от изменения смеси задач, утечки выборки, ложного оценщика или тяжёлых нарушений, компенсируемых успехом на других задачах.

Мой вывод: интегрирование уменьшает зависимость от одного выбранного порога, но метрика по-прежнему зависит от области интегрирования, k, весов задач, бюджета и определения успеха. Если оценщик ошибочно называет все обходы успехами, любой агрегатор его бинарных меток также оценит их высоко.

Поэтому сохраняется конструкция
\[
Admission=AuthenticEvidence\land RequiredConstraints
\land AbsoluteCapability\land EvaluationRule.
\]

Интегрированная метрика может входить в EvaluationRule стохастического расширения после определения выборки и неопределённости. Она не отменяет остальные конъюнкты и не превращает конечный G12 в IID-сертификат. В опубликованном эталоне такой новый статистический профиль не добавлялся.

### Для декомпозиции не нужен намеренно ослабленный checker

Проверка готового доказательства и поиск доказательства — разные вычислительные задачи. Строгий checker вполне совместим с ограниченным поиском, который возвращает UNKNOWN. Именно так устроен F2 в 1.3. Полезность планирования измеряется тем, удаётся ли дешевле найти подходящий term, а не тем, добавляет ли декомпозиция логические следствия к полному решателю.

Также нужно различать: допустимость эвристики A*, логическую soundness сертификата, эмпирическую калибровку предсказания и отсутствие ложного отсечения решений. Это разные обязательства. Типизация не доказывает достижимость цели; отсутствие контрпримера в ограниченном тесте не выдаёт универсальный сертификат.

### Результат f∘g не доказывает «только RL способен учить композиции»

[Исходная работа](https://arxiv.org/pdf/2509.25123) показывает преимущество композиционного RL над исследованным RFT в контролируемом сетапе и перенос на более сложные композиции. Это важное эмпирическое свидетельство, но не теорема о невозможности обучить композицию другим методом, данными или моделью. В языке следует сохранять общий интерфейс Update и отдельно проверять полученный артефакт, не зашивать исключительное право RL в семантику.

### Остальные сильные формулировки требуют сужения

- Проценты «35% ТРИЗ», «70% практики», «5% механизации» без операционального знаменателя — оценки автора, не сопоставимые измерения. Проверку всех исторических тезисов о ТРИЗ этот пересмотр не проводил.
- Сходство формул task arithmetic и differential evolution не устанавливает равенство полных алгоритмов: различаются распределение родителей, выбор масштаба, recombination и отбор. Классификация по осям полезна; знаки строгой эквивалентности требуют отдельного доказательства.
- «Append-only verifier — единственная безопасная форма изменения» слишком сильно. Добавление неверного или невыполнимого теста тоже может блокировать все релизы. Изменения оценщика требуют отдельной проверки версии и корректности, даже если старые тесты сохранены.
- Порча метрики не всегда необратима: если сохранились подлинные исходные наблюдения, новый оценщик может пересчитать результаты. Если сохранены только сфабрикованные метки, восстановление действительно может оказаться невозможным.
- Детерминированный счётчик циклов устраняет один источник шума, но не позволяет без дополнительных контролей приписать весь разброс только харнесу. Состояние инференса, планирование, входы и окружение тоже могут меняться.
- Оптимизация объявленных симуляторных циклов не становится reward hacking только потому, что не ускоряет другое физическое устройство. Нужно проверить заявленную цель: перенос на железо — отдельное обязательство, если он был обещан.
- Остаток дисперсии и разрыв между порогами 50/90 не являются универсально «багом харнеса» или единственной мерой нестабильности. Для причинной атрибуции нужны повторения и модель взаимодействий факторов.

## 6. Следствие для процедуры аудита

Полезное дополнение — карточка находки с раздельными полями:

```text
Finding = {
  target_version, artifact_digest,
  observed_behavior, reproducer, execution_result,
  normative_clause, clause_scope, attacker_capabilities,
  conformance_verdict, application_impact,
  resolution, regression_reference
}
```

Статусы наблюдения: REPRODUCED / NOT_REPRODUCED / NOT_CHECKED. Статусы соответствия: VIOLATION / WITHIN_DECLARED_SCOPE / UNRESOLVED. Оценка пригодности хранится независимо. Например, WITHIN_DECLARED_SCOPE может сочетаться с BLOCKING_FOR_DEPLOYMENT.

Это предлагаемый формат отчётности, а не новая исполняемая инструкция AHSL. Он предотвращает оба ошибочных вывода: «можно воспроизвести, значит спецификация ложна» и «описано в ограничениях, значит опасность устранена».

## 7. Решение по выпуску

Новых воспроизведённых дефектов реализации AHSL 1.3 этот материал не установил. Подтверждён исторический дефект аттестации и уточнена классификация ряда прежних обвинений. Полезные усиления 1.3 сохраняются; требования к будущей изоляции и внешним адаптерам остаются открытыми и явно обозначенными. Приложенный отчёт не даёт основания заменять жёсткий допуск одной усреднённой метрикой или ослаблять checker.
