# AHSL: ответ на аудит и пересмотр приоритетов

Дата: 2026-09-06. Проверена локальная реализация `ahsl-1.0`. Статус документа: результаты адресной перепроверки, редакционные исправления и план следующей реализации. Исполняемые R06/F1 и архив AHSL 1.0 не изменены.

## 1. Решение

Сохранить R06/F1 как ограниченные исполняемые эталоны. До расширений декодирования приоритет получают происхождение свидетельств, восстановление после UNKNOWN и демонстрация полезной композиции при одинаковом вычислительном бюджете. Название `EXECUTABLE_REFERENCE` характеризует наличие точного операционного эталона; из него не следует машинное доказательство соответствия всей спецификации.

Предыдущая спецификация уже отделяла X1 от реализации и оговаривала доверие к оценщику, но эти оговорки не заменяют отсутствующие адаптеры. В рабочий `AHSL-specification.md` внесены раннее предупреждение о границах, недостающие схемы, байтовое описание ограниченного F1-алфавита и точное описание проверок. Исторический пакет сохранён для воспроизводимости.

## 2. Что перепроверено

Выполнены 19 существующих unit tests F1 и короткие адресные сценарии. Код сценариев и их результат приведены в приложениях. TLC, независимый обход 69 475 состояний, 40 000 состязательных событий и 16 000 случайных реестров из пользовательского аудита здесь не повторялись.

### Границы доверия

Воспроизведение с renamed sample использует роль provider. Агентская роль не получает право assessment через изменение id. Дефект расположен в протоколе поставки доказательных данных: доверенный оценщик или его адаптер может представить старый опыт как новый. Формальный учёт строк этого не обнаруживает.

Подмена F1-состояния требует возможности менять внутренний объект. F1 обещает переход только из состояния, полученного через initial/step; аутентификация произвольного snapshot не реализована. Значит, это блокирующее условие интеграции с недоверенным хранилищем/агентом, но не опровержение soundness на достижимых состояниях. Добавленный hash, который атакующий тоже пересчитывает, эту границу не защищает.

Требование вызвать `invariants` после каждого step не является единственным способом обеспечить инвариант. Достаточны корректное построение переходов и доказательство сохранения. Нынешний недостаток — отсутствие полного доказательства реализации и явного протокола восстановления; тестовые assertions покрывают лишь выполненные пути.

## 3. Что именно не демонстрирует F1

Обозначим через Ω(K) непустое множество моделей Scope. База B состоит из формул, истинных во всей Ω(K). Каждая принятая схема удовлетворяет

\[
K\models(\bigwedge_i p_i)\Rightarrow g.
\]

Введём независимо от Python-поля ranks:

\[
V_0=B,\quad V_{j+1}=V_j\cup\{g:\exists s,\ Checked(s)\land needs(s)\subseteq V_j\}.
\]

**Доказательство soundness абстрактного замыкания.** Для V_0 утверждение следует из корректности прямых сертификатов. Если все элементы V_j истинны в каждой модели K, то для новой цели все premises истинны в каждой такой модели. Корректность импликации даёт истинность цели. Поэтому каждый элемент объединения V_j следует из K. Присваивание ranks конкретным обходчиком в доказательстве не используется.

В F1 direct certify полностью перебирает ту же Ω(K). Поэтому

\[
V_*\subseteq\{v:certify(v)\text{ семантически успешен}\}.
\]

Это не означает V*=∅ или V*=B: композиция действительно может добавлять узлы реестра. Но она не достигает целей, недоступных прямому полному проверяющему механизму. При непустых premises её собственный тариф выше прямой проверки; при пустых — равен. «В пять раз» не является общей константой: в воспроизведённом примере полная композиция стоит 23/5=4,6 раза дороже.

### Исправление: отделить поиск свидетельства от проверки

Нужны два интерфейса будущего профиля, условно F2:

```text
FindWitness(problem, budget) -> Found(witness, cost) | Unknown(cost)
CheckWitness(problem, witness, budget) -> Valid(cost) | Invalid(cost) | Unknown(cost)
```

CheckWitness должен оставаться корректным и однозначным в пределах профиля. Ограниченным является доступный поиск и/или ресурс проверки. Полный решатель конечной задачи также может быть ограничен бюджетом — логическая неполнота сама по себе не цель. Проверка готового доказательства и решение истинности произвольного утверждения — разные задачи.

Начальный вариант — ограниченный язык программ с явной семантикой и небольшим ядром проверки доказательств. Например, композиция двух частично корректных программ обосновывается правилом

\[
\frac{\{P\}\ a\ \{Q\}\qquad\{Q\}\ b\ \{R\}}
{\{P\}\ a;b\ \{R\}}.
\]

Завершение и пределы ресурсов требуют дополнительных обязательств; это правило само их не устанавливает. Для работы со сменой окружения нужны также зависимости и условия применимости.

Условие полезности F2: на заранее определённом семействе свежих задач декомпозиция находит и проверяет результат при бюджете B, а сопоставимый прямой поиск при том же B даёт UNKNOWN либо имеет большую стоимость. Обе стороны используют одну семантику, один trusted checker и одинаковый доступ к ранее доказанным леммам. Время генерации подзадач, неудач, проверки связей и хранения учитывается. Нельзя искусственно сделать direct дорогим тарифом или дать только композиции бесплатную библиотеку ответов.

Один положительный пример доказывает существование преимущества в данном опыте; устойчивое преимущество требует независимых задач и запусков. Нынешние F1-тесты такую гипотезу не проверяют.

## 4. Статистическое свидетельство как результат управляемого опыта

Предлагаемое исправление R06/X1 — связывать assessment с заданием оценщику, созданным до раскрытия результата:

```text
TrialAssignment = {
  trial_ref, candidate_ref, parent_ref, protocol_ref,
  environment_ref, sampler_ref, reset_contract_ref,
  generation, evaluator_ref
}

SampleReceipt = {
  assignment_ref, unit_index, input_ref, execution_ref,
  outcome_ref, cost_ref, producer_attestation_ref
}
```

Это проект схемы нового профиля, не утверждение о его нынешней реализации. Полный нормативный алфавит и канонизация должны быть зафиксированы перед внедрением.

Идентичность оценочной единицы выдаёт доверенный runner в рамках Assignment. Provider не выбирает новое имя для старого результата. Receipt связан с protected execution log; при удалённой передаче используется аутентифицированное подтверждение производителя. Криптографическая подпись устанавливает отправителя, но сама не доказывает, что тот выполнил эксперимент честно.

Повтор receipt отклоняется независимо от внешней метки. Смена имени не меняет факта уже учтённого запуска. Совпадающие бинарные исходы двух честных опытов не основание для запрета: all-wins естественно может повториться. Поэтому дедупликация по массиву результатов неверна.

Генератор заданий и сброс адаптивного состояния также находятся вне изменяемого кандидата. Для проверок на свежих репликах Assignment закрепляет, когда выбирается случайность и что известно кандидату. Если протокол разрешает повторное использование общего набора данных, оно должно учитываться соответствующим статистическим методом; новая строка id не превращает такую оценку в свежую независимую реплику.

Union bound не требует независимости между слоями. Нужны корректные условные p-values для каждой проверки и общий бюджет ошибки, включая адаптивный выбор последующих кандидатов. Следующий набор проверок должен включать несколько слоёв, несовпадающие флаги gain, частичный провал слоя, несколько trials и непустые области отклонения на рабочих размерах. Точный Fractions-код полезен, но не подтверждает предпосылки генерации данных.

## 5. UNKNOWN: учёт и возможность продолжения

Автоматически возвращать резерв при timeout нельзя: операция могла выполниться и потребить ресурсы. Нынешняя модель корректно оставляет обязательство открытым, но не предусматривает административный terminal-переход при окончательно пропавшем провайдере.

Новый профиль должен выбрать и формализовать один из путей:

1. Reconcile по достоверной квитанции: установить исход и реальные расходы, затем закрыть.
2. Закрыть как unresolved: консервативно списать полный известный верхний предел, отозвать поколение записи и сохранить неразрешённое внешнее обязательство отдельно от успешного результата.

Второй путь требует реально обеспеченного верхнего предела стоимости и защиты от поздних побочных эффектов. Поздняя квитанция не должна повторно списывать стоимость или восстанавливать старые права; правила корректировки расходов определяются заранее. Терминальное состояние учёта не означает, что неизвестное физическое действие отменено.

Supervisor-событие должно поступать через доверенный адаптер. Включать часы внутрь детерминированного ядра не требуется: истечение deadline может быть зарегистрированным внешним событием. Liveness формулируется при явных предпосылках о доставке и выполнении восстановления; она не следует из отключения deadlock check.

### Replay не доказывает мир целиком

Определим для журнала L:

\[
Consistent(M,L)\iff\forall\tau\in L,\ Replay(M,\tau)=Observed(\tau).
\]

Из этого не следует совпадение M с настоящей средой вне L. Две программы могут совпадать на всех проверенных переходах и расходиться на следующем действии. Можно даже построить таблицу, которая запоминает весь L и ошибается в любом новом случае.

Название статуса AHSL должно отражать область: `ReplayConsistent(model_ref, log_root, comparison_contract)`. Квалификация на новом журнале получает отдельный report. Универсальная эквивалентность допустима только с отдельным доказательством и его предпосылками. BFS даёт кратчайший путь в конкретном графе при соответствующих условиях поиска; он не доказывает, что настоящий мир имеет этот граф. Нулевое число внешних действий во время симуляции не означает нулевую вычислительную стоимость.

В самой schema есть проверка предсказания при реальном исполнении и остановка плана после расхождения. Это полезная часть архитектуры. Для AHSL нужны также сравнение на намеренно новых переходах и учёт предпосылок, отличающих конкурирующие модели. Проспективная проверка корректна условно на принятую модель; выбор модели остаётся задачей исследования.

### Механизм как состояние

Можно представить текущий исследовательский процесс как S=(Π,C,E,M,A,L): механизм, накопленный контекст, версия среды, память, архив и журнал. Замороженные Mission/Policy принадлежат управляющей части, а не редактируемому Π. Изменение Π создаёт новую версию; допустимость её активации проверяет внешний переход. Если кандидат включает обе task/meta-функции, идентичность закрепляет обе.

Преимущество обновлённого Π оценивается по распределению результатов его полных сегментов при одинаковом бюджете. Один удачный потомок не удостоверяет превосходство оператора. Φ — сжатое наблюдение; отброшенные им детали могут влиять на выбор следующего эксперимента, поэтому сводка сохраняет ссылки на исходные записи и собственную версию.

Эти сущности стоит сделать стандартными типами библиотеки. Новый kernel primitive требуется там, где меняются права, эффекты или правила активации, а не из-за нового названия алгоритма.

## 7. ТРИЗ: полезный протокол постановки задачи

В прочитанном [SKILL.md](https://github.com/snow-ghost/triz/blob/main/skills/triz/SKILL.md) действительно требуется установить пользу и вред одного вмешательства; рутина и вопросы, решаемые измерением, направляются по более простому пути. Это методические инструкции LLM, не самостоятельный доказательный решатель.

Для AHSL полезен библиотечный объект Contradiction с вмешательством, условиями, двумя эффектами, причинным объяснением и ссылками на свидетельства. Допустим отдельный статус HYPOTHESIZED: предположенная причинная связь не получает Fact только из-за заполненного поля. Unknown приводит к измерению. Сепарация по времени, месту или условиям — операторы генерации вариантов; их результат оценивается по исходным ограничениям.

Ни конфликт желаемых метрик, ни consensus council, ни формальный вид карточки не удостоверяют причинность. Если противоречие не установлено, обычный эксперимент или исправление дефекта остаются допустимым исходом. Переносить весь каталог ТРИЗ в ядро оснований нет.

## 8. Новый порядок реализации

| Приоритет | Результат | Условие завершения |
|---|---|---|
| P0: точность стандарта | Закрытые схемы/коды, байтовая грамматика, таблица claim → доказательство → код → тест → предпосылки | Независимые реализации совпадают на golden vectors; отсутствующие доказательства явно отмечены |
| P1: доверенная граница | Runner выдаёт Assignment/Receipt; внешний snapshot не становится состоянием по умолчанию | Старый запуск не проходит как новый после переименования; ложный сертификат и пересчитанный hash не восстанавливают доверие |
| P2: восстановление | Терминальный протокол для UNKNOWN и поздних ответов | Нет возврата неизвестной стоимости; полная трасса показывает завершение учёта и запрет устаревших эффектов |
| P3: полезная композиция | FindWitness/CheckWitness и проверяемые правила композиции | Выигрыш на свежих задачах при общем бюджете, одинаковых леммах и неизменном checker |
| P4: расширяемое исследование | Версионируемые Π, EnvironmentArtifact и ReplayConsistent | Обновления не меняют корневую оценку; ложная модель мира ограничивает или останавливает исполнение |
| P5: ускорение | Prefix caching, speculative decoding, затем перенос KV/латентный канал | Ускоряется уже квалифицированный цикл при сохранении объявленных гарантий |

Для P0 модель покрытия должна различать математическое утверждение, model checking конечной абстракции, conformance testing и theorem о refinement. Количество посещённых состояний не заменяет ни одну из этих связей.

Этот план сохраняет исходную цель: уменьшить стоимость получения проверенного результата. Центральный следующий эксперимент — показать полезность проспективной композиции в исполняемой задаче. Новые ускорители получают смысл после того, как ясно, какой именно достоверный процесс они ускоряют.

## Приложение B. Код адресных воспроизведений

Запускать сохранённый скрипт как `audit-work/reproduce.py` рядом с неизменённым каталогом `ahsl-1.0`. Он пишет только `audit-work/results.json`. Существующие тесты F1 отдельно запускаются командой `python3 -m unittest discover -s tests -p test_prospection.py` из каталога `ahsl-1.0`.

```python
'''Focused audit reproductions; leaves the reference packages unchanged.'''

from copy import deepcopy
import hashlib
import importlib
import json
from pathlib import Path
import sys


ROOT = Path(__file__).resolve().parents[1]
PROFILE = ROOT / 'ahsl-1.0'
sys.path.insert(0, str(PROFILE))
sys.path.insert(0, str(PROFILE / 'runtime_0_6'))

p = importlib.import_module('prospection')
evidence = importlib.import_module('evidence')
scenario = importlib.import_module('examples.scenario')
fixture, report, value = scenario.fixture, scenario.report, scenario.value
core = importlib.import_module('kernel.core')
system = importlib.import_module('system')


def f1_check():
    scope = {
        'environment': 'h' + '0' * 64,
        'definitions': 'h' + '1' * 64,
        'atoms': ['a', 'b'],
        'assumptions': [],
    }
    state = p.initial(scope, 1000)
    a = ['or', ['atom', 'a'], ['not', ['atom', 'a']]]
    b = ['implies', ['atom', 'b'], ['atom', 'b']]
    ids = []
    for i, formula in enumerate((a, b, ['and', a, b], ['bottom'])):
        state, answer = p.step(state, {
            'id': f'd{i}', 'kind': 'declare', 'formula': formula,
        })
        ids.append(answer['claim'])
    start = deepcopy(state)
    state, answer = p.step(state, {
        'id': 'sketch', 'kind': 'sketch', 'target': ids[2],
        'premises': sorted(ids[:2]),
    })
    assert answer['code'] == 'SKETCH_ACCEPTED'
    statuses = [p.status(state, ids[2])]
    for i, claim in enumerate(ids[:2]):
        state, answer = p.step(state, {
            'id': f'c{i}', 'kind': 'certify', 'claim': claim,
        })
        assert answer['code'] == 'CHECKED'
        statuses.append(p.status(state, ids[2]))
    direct, answer = p.step(start, {
        'id': 'direct', 'kind': 'certify', 'claim': ids[2],
    })
    assert answer['code'] == 'CHECKED'
    forged = deepcopy(start)
    forged['certificates'][ids[3]] = 'h' + 'f' * 64
    forged, _ = p.step(forged, {
        'id': 'trigger', 'kind': 'note', 'claim': ids[3],
        'tag': 'hypothesis', 'payload_hash': 'h' + '2' * 64,
    })
    return {
        'and_composition_statuses': statuses,
        'composed_cost_after_declarations': state['spent'] - start['spent'],
        'direct_cost_after_declarations': direct['spent'] - start['spent'],
        'forged_internal_state_false_claim': p.status(forged, ids[3]),
        'forgery_is_outside_reachable_state_precondition': True,
    }


def r06_checks():
    policy, registry, configuration = fixture()
    state = system.initial(policy, registry, configuration)
    serial = 0

    def send(principal, kind, **payload):
        nonlocal state, serial
        serial += 1
        state, answer, requests = system.step(state, principal, {
            'id': f'e{serial}', 'kind': kind, **payload,
        })
        assert system.invariants(state)
        return answer, requests

    candidate = deepcopy(configuration)
    candidate['program']['fuel'] += 1
    send('agent', 'propose', proposal='p', configuration=candidate)
    verdicts = []
    for i, prefix in enumerate(('sample', 'sample', 'RENAMED')):
        trial = f't{i}'
        send(
            'agent', 'start_trial', trial=trial, proposal='p', claim='improve',
        )
        answer, _ = send(
            'provider', 'assessment', trial=trial, charge=6,
            outcome={'kind': 'report', 'report': report(prefix=prefix)},
        )
        verdicts.append(answer['verdict']['code'])
    publish, _ = send('agent', 'publish', trial='t2')
    assert state == system.replay(
        policy, registry, configuration, state['log'],
    )

    renamed = {'assessment_codes': verdicts, 'publish_code': publish['code']}
    state = system.initial(policy, registry, configuration)
    send('agent', 'start_run', run='run', args={'x': value(1)})
    _, requests = send('agent', 'drive', run='run')
    job_id = requests[0]['request']['job']
    send('provider', 'deliver', run='run', event={
        'id': 'unknown', 'kind': 'unknown', 'job': job_id,
    })
    send('supervisor', 'invalidate_context', context='environment-v2')
    close, _ = send('agent', 'close_run', run='run')
    kernel = state['runs']['run']['kernel']
    _, cancel, _ = core.step(kernel, 'supervisor', {
        'id': 'cancel', 'kind': 'cancel', 'job': job_id,
    })
    _, agent_cancel, _ = core.step(kernel, 'agent', {
        'id': 'agent_cancel', 'kind': 'cancel', 'job': job_id,
    })
    held = kernel['jobs'][job_id]['held']
    send('provider', 'deliver', run='run', event={
        'id': 'settle', 'kind': 'complete', 'job': job_id, 'charge': held,
        'outcome': {'kind': 'failure', 'code': 'STOPPED'},
    })
    settled_close, _ = send('agent', 'close_run', run='run')
    unknown = {
        'close_before_settlement': close['code'],
        'supervisor_cancel_code': cancel['code'], 'held': held,
        'agent_cancel_code': agent_cancel['code'],
        'close_after_provider_completion': settled_close['code'],
    }

    multi = deepcopy(policy)
    multi['strata']['aux'] = deepcopy(multi['strata']['composition'])
    multi['strata']['aux']['gain'] = False
    data = report()
    data['strata']['aux'] = report(prefix='aux')['strata']['composition']
    accepted = evidence.assess(multi, 1, 'improve', data)
    data['strata']['aux'] = report(
        prefix='aux', parent=True, candidate=False,
    )['strata']['composition']
    rejected = evidence.assess(multi, 1, 'improve', data)
    return {
        'sample_rename': renamed, 'unknown': unknown,
        'two_strata_function_check': {
            'positive': accepted['code'], 'negative': rejected['code'],
            'threshold': accepted['threshold'],
            'tests': sorted(accepted['tests']),
            'is_union_bound_proof': False,
        },
    }


def main():
    tracked = (
        'prospection.py', 'tests/test_prospection.py',
        'runtime_0_6/system.py', 'runtime_0_6/evidence.py',

    output.write_text(json.dumps(result, indent=2) + '\n', encoding='utf-8')
    print(json.dumps(result, indent=2))


if __name__ == '__main__':
    main()
```
