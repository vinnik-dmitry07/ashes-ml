# BOUND_EVIDENCE_1: исполняемый профиль доверия

Версия 0.2, 10 сентября 2026. Реализация: `llmbench/trust.py` и `llmbench/evidence_views.py`. Встроенное ядро AHSL 1.4 не изменено. Валидаторы и редуктор этих модулей определяют принимаемые объекты; этот текст объясняет их контракт и область утверждений.

## 1. Граница доверия

Владелец управляет реестром checker’ов и жизненным циклом свидетельств. Предлагатель передаёт данные, но не функции Python, готовые вердикты или полномочия. Хост владеет `EvidenceLedger`, секретным HMAC-ключом, журналом и непередаваемым через JSON объектом `owner_handle`. Строка `owner` не является этим объектом.

Это проверяемая граница вызовов в доверенном Python-хосте. Произвольный Python в том же процессе сможет получить внутренние поля и обойти её; такая модель угроз не покрывается. Владелец не должен передавать модели ledger, ключ или handle. Недоверенный текст и результат LLM сами по себе не могут отозвать доверие. Поле причины отзыва фиксирует решение владельца, но не доказывает его обоснованность.

Три доступных профиля вызывают заранее определённые детерминированные функции. Регистрация произвольного callback или исполняемого текста не поддерживается. Проверка F2 утверждает выводимость в заданном формальном фрагменте. Проверка G12 утверждает согласованность трассы с фиксированной средой; она **не удостоверяет**, что трассу породила настоящая LLM.

## 2. Идентичность checker’а и свидетельства

`Checker` содержит `profile`, закрытые `parameters`, `source_manifest`, `protocol=BOUND_EVIDENCE_1`, а также реализацию Python и три компонента её версии. Его ID — `digest('Checker', definition)`. Смена параметров, исходников или этой версии Python меняет идентичность. Название само по себе не переносит доверие.

`source_manifest` измеряется и проверяется по файлам пакета. Он не удостоверяет весь хост, бинарник Python, ОС или происхождение внешних данных. После изменения исходников нужен новый снимок. Автоматического импорта старого журнала в изменённую реализацию в этом профиле нет.

`submit(checker, artifact, claim, context)` получает закрытые объекты текущего профиля. Артефакт, ожидаемое утверждение и контекст кодируются каноническим AHSL JSON и хранятся в hex-полях. Это сохраняет самостоятельные границы глубины AST при включении в снимок состояния. Лимит каждого исходного объекта — 262144 байта. Канонический формат ядра исключает дубли ключей, циклы, нестандартные числа и альтернативные кодировки.

Успешная проверка создаёт `EvidenceReceipt` с полями:

| Поле | Значение |
| --- | --- |
| `kind` | `EvidenceReceipt` |
| `checker` | ID измеренного определения checker’а |
| `artifact`, `context` | Дайджесты точных упакованных входов |
| `claim` | Структурированное утверждение, заново построенное checker’ом |
| `scope` | Область применимости текущего профиля |
| `dependencies` | Проверенные ссылки на предыдущие свидетельства |
| `depth` | Глубина графа зависимостей, от 1 до 64 |
| `supersedes` | Старое свидетельство при повторной проверке, иначе `null` |
| `check_sequence` | Номер события начала этой проверки |
| `artifact_hex`, `claim_hex`, `context_hex` | Канонические входы для повторной проверки |

ID квитанции вычисляется по всем этим полям. Даже повторная проверка того же артефакта получает новый номер события и новый ID. Ожидаемый `claim` должен точно совпасть с измеренным; подпись кандидата «прошёл» не используется. HMAC аутентифицирует события хоста, а не превращает содержимое кандидата в факт.

## 3. Закрытые проверяющие профили

| Профиль | Параметры | Проверка и утверждение |
| --- | --- | --- |
| `F2_PROOF_1` | `fuel`: 1–100000 | Артефакт `{goal, term, library}`; контекст `{library: cid('ProofLibrary', library)}`. Вызов `certify` с точным goal, term и библиотекой; результат `{kind: Proposition, goal: digest('Formula', goal)}`. Scope — дайджест контекста. |
| `G12_TRACE_1` | `max_steps`: 1–64; `require_goal`: bool | `audit_trace` заново проверяет каждый переход; число шагов ограничено; при `require_goal=true` нужна истинная цель. Контекст содержит точный `ENVIRONMENT`. Утверждение `{kind: TraceConsistency, trace: cid, ground_success: bool}`. Scope — `ENVIRONMENT`. |
| `EVIDENCE_BUNDLE_1` | `{}` | Артефакт и claim содержат один отсортированный список уникальных `members`. Все члены существуют, допустимы и имеют общий scope. Контекст `{member_scope: scope}`. Утверждение — `EvidenceBundle`; зависимости берутся из проверенного списка. |

У F2 использованные библиотечные доказательства проверяются при обращении к ним; квитанция не утверждает корректность каждого неиспользованного элемента библиотеки. Точное окружение остаётся частью входа. Подмена смысла цели меняет утверждение и не может выдать доказательство исходной формулы.

В пакете не существует автоматического перевода естественно-языкового требования в гарантированно правильную формулу. Корректная формализация цели остаётся обязанностью владельца. Для G12 команда `paint` может дать внешнюю награду, но не истинный успех.

Результат проверки: `CHECKED` с ID квитанции, `REJECTED` с конечным кодом ошибки или `INCOMPLETE` при исчерпании F2 fuel. `INCOMPLETE` не доказывает ложность утверждения и не даёт допуска. Повторная проверка с другим fuel требует зарегистрированного владельцем нового определения.

## 4. Допустимость в текущем состоянии

Пусть `closure(r)` содержит r и все его транзитивные зависимости. Пусть `barrier(a)` — последнее событие карантина или отзыва точного артефакта a, а при отсутствии события — −1. Тогда:

```
eligible(r) iff for every x in closure(r):
    receipt_status(x) == ACTIVE
    and checker_status(checker(x)) == ACTIVE
    and check_sequence(x) >= barrier(artifact(x))
```

Дополнительно потребитель обязан проверить scope и назначение. Граф ацикличен по построению: квитанция ссылается только на ранее созданные записи. У пакета не более 64 непосредственных членов, глубина не более 64; один обход ограничен 2048 уникальными квитанциями. Ромб зависимостей не умножает одно свидетельство в несколько независимых.

Это точное условие допуска **свидетельств**. Назначение `publish` не выпускает новую агентную программу и не доказывает `improve`. Независимость статистических наблюдений из графа не следует.

## 5. Карантин, отзыв и восстановление

`change_trust(owner_handle, target, id, status, reason)` допускает `target` из `{receipt, checker}`, `status` из `{QUARANTINED, REVOKED}`. `reason` содержит непустой код до 120 символов и до 64 ссылок на существующие свидетельства. Повтор того же статуса запрещён; `REVOKED` терминален. Операции прямого перевода обратно в `ACTIVE` нет.

При карантине или отзыве квитанции ставится барьер на **точные байты артефакта**. Все его старые дубликаты и их зависимости блокируются. Обычная повторная отправка этих байтов также отклоняется. Это предотвращает обход отзыва выбором другой уже выданной квитанции. Семантически эквивалентные переписи с другими байтами автоматически не обнаруживаются. Если дефект относится ко всему правилу проверки, владелец должен вывести из доверия checker, а не только один пример.

`revalidate(owner_handle, old_receipt, checker)` повторно проверяет те же artifact, claim и context. Он не меняет старую запись и не заменяет цель. Успех создаёт новое свидетельство с `supersedes`; неуспех оставляет старое недопустимым. Старые зависимости автоматически на новый ID не переписываются: пакеты нужно проверить и построить заново. Квитанция под отозванным checker’ом не оживает от регистрации другого checker’а.

Замена профиля с `require_goal=false` на `true` демонстрирует содержательную разницу: согласованная неуспешная трасса раньше могла пройти проверку согласованности, но не проходит новую проверку достижения цели. Новая оценка не копируется из старого вердикта.

## 6. Потребители и устаревание кэша

`TrustedMemory.read(scope)` возвращает только актуально допустимые структурированные утверждения. Карантин не приводит к выдаче исходного текста под менее доверенной меткой. `prepare` создаёт подписанный объект разрешения: корни, scope, назначение, уникальные листья, контрольную проекцию checker’ов и текущую голову журнала.

`consume` заново проверяет HMAC, назначение, область и актуальную допустимость всей зависимости. Добавление постороннего свидетельства не инвалидирует кэш; отзыв значимой зависимости инвалидирует. `issued_head` записывает момент выдачи, но не является бессрочным разрешением.

`dataset` создаёт кандидат на экспорт. Для `training` разрешены только доказанные формулы и трассы с истинным успехом. Повторное свидетельство точного артефакта не дублирует строку датасета. Формулы помечаются `CHECKED_FORMULA`, трассы — `SYNTHETIC_VALIDATED_TRACE`: происхождение от живой модели не утверждается. Проверка датасета пересчитывает его хеш, разрешение и каждую строку по листьям.

`export_dataset` удерживает блокировку ledger на протяжении проверки и записи файла, не допуская гонку с отзывом в этом экземпляре хоста. Файл открывается только как новый, затем выполняются flush и fsync. Частичный сбой записи может оставить неполный файл; атомарная замена файлов и автоматическое удаление повреждённого экспорта не реализованы. Исторический экспорт нужно вновь валидировать перед обучением. Уже прочитанные промпты, опубликованные копии или веса обученной модели автоматически не отзываются.

`guard(authorization, purpose)` позволяет доверенному потребителю удерживать ту же блокировку до завершения своего локального действия. Обычная выдача данных задаёт проверку в момент чтения, а не вечную гарантию после возврата. Несколько процессов без общего владельца ledger этот контракт не образуют.

## 7. Поведенческий дескриптор

`G12_BEHAVIOR_1` строится по заново проверенной трассе: число шагов, счётчики действий, движения назад и истинный успех. Ячейка архива содержит успех, `steps // 8`, наличие возвратов и наличие `paint`. Никакой текстовый самоотчёт о поведении не входит в признаки.

Неиспользуемая функция, иной program ID или убедительная подпись не создают новую ячейку при той же измеренной траектории. Изменение реальных действий может её изменить. `BehaviorArchive.cells()` фильтрует недопустимые квитанции при чтении.

Это независимое от пропозера измерение конкретных свойств G12. Оно не доказывает семантическое разнообразие всех программ, не является полным MAP-Elites и не гарантирует качество поведения внутри разных ячеек.

## 8. Журнал, лимиты и аварии

Каждый переход выполняется на копии состояния. Перед записью проверяется кодируемость всей следующей проекции, а не только входящего события. Пределы канонического кодека сохраняются при накоплении записей. Затем хост пишет подписанное событие с результатом в append-only журнал и выполняет fsync. Только после этого публикуется новое состояние.

`START` долговечно резервирует одну проверку до её выполнения; `FINISH` запускает встроенный checker и записывает результат. Невалидная схема верхнего уровня или превышение размера не начинает проверку. Отклонённое доказательство после `START` расходует проверочную квоту; оно не блокирует хороший артефакт ложным claim. По умолчанию доступны 256 проверок, 2048 событий и 16 миллионов байт журнала. Конфигурация допускает максимум 10000 проверок и 100000 событий; ограничения канонического снимка действуют дополнительно.

Для каждого незавершённого `START` резервируется место одного события `FINISH` и 2048 байт журнального завершения. Это не резерв CPU в реальном времени и не отдельная гарантированная полоса для команд владельца. При исчерпании общего бюджета новые изменения могут отклоняться. Глубина, размер входа, число проверок и fuel ограничены, но профиль не заявляет защиту сервиса от всех перегрузок транспорта и хоста.

Прерывание чистого checker’а после `START` оставляет pending-запись. `resolve_pending` доступен владельцу в том же экземпляре и повторяет чистую проверку без новой квоты. Если следующая проекция превышает лимит кодека, она не публикуется; завершение pending не гарантируется при недостатке вместимости. После I/O-ошибки записи экземпляр переходит в закрытое состояние: новые изменения и разрешения запрещены, статус — `UNAVAILABLE`. Нельзя продолжать пользоваться старым доверием после неясного результата fsync.

`replay(path, key, identity, expected_head)` проверяет исходники, идентичность владельца, цепочку, HMAC и внешний якорь, заново выполняет каждый чистый checker и сравнивает результаты. Он возвращает проверенную проекцию и её дайджест. Реплей доступен только для чтения; writable resume после перезапуска, восстановление повреждённого хвоста и межверсионная миграция требуют отдельного механизма. Опубликованный тестовый ключ обеспечивает воспроизводимость примера, но не противодействие подделке владельцем этого ключа.

## 9. Минимальный локальный пример

Код выполняется в доверенном хосте из корня пакета. Нужна новая директория для журнала; пример хранит секрет только в памяти.

```python
import secrets
from pathlib import Path
from tempfile import TemporaryDirectory

from ahsl.codec import cid
from llmbench.evidence_views import TrustedMemory
from llmbench.experiment import check_sources
from llmbench.protocol import digest
from llmbench.trust import EvidenceLedger

with TemporaryDirectory() as directory:
    ledger = EvidenceLedger(
        Path(directory) / 'trust.jsonl', secrets.token_bytes(32),
        check_sources(),
    )
    owner = ledger.owner_handle
    checker = ledger.register(owner, 'F2_PROOF_1', {'fuel': 100})
    p = ['atom', 'P']
    goal = ['imp', p, p]
    result = ledger.submit(
        checker,
        {'goal': goal, 'term': ['lam', p, ['var', 0]], 'library': {}},
        {'kind': 'Proposition', 'goal': digest('Formula', goal)},
        {'library': cid('ProofLibrary', {})},
    )
    receipt = result['receipt']
    memory = TrustedMemory(ledger)
    memory.add(receipt)
    scope = ledger.receipt(receipt)['scope']
    assert len(memory.read(scope)) == 1
    ledger.change_trust(
        owner, 'receipt', receipt, 'QUARANTINED',
        {'code': 'owner_review', 'evidence': []},
    )
    assert memory.read(scope) == []
    ledger.close()
```

## 10. Сила проверки

Регрессионные тесты проверяют стыки, включая дубликаты, подмену claim и библиотеки, смену checker’а, устаревший экспорт, квоты, прерванную проверку, fsync-ошибку и сохранение кодируемости снимка. Автономный перебор сравнивает реализацию с независимо записанным булевым условием для двух листьев, пакета и двух checker’ов: 3⁵=243 конфигурации, 2916 проверок потребителей.

Это ограниченная исполнимая проверка, а не машинное доказательство корректности всех графов, хостов и будущих профилей. Она не оценивает вероятность prompt injection у LLM. Спецификация и журнал делают конкретные утверждения проверяемыми; истинность внешней формализации и доверенность хоста остаются явными предпосылками.
