# AHSL 1.4: решения по двум дефектам и отдельное расширение improve

Исходная база — присланный AHSL-1.3(1).zip. SHA-256 исходного архива:
`85928587c9c333472c9d9fa2749cdc1c55c0b874f4be7b0d0e89c3cd39c70178`.
Аудит 1.0 не считается проверкой кода 1.3. Исторический отчёт 1.3 сохранён
в `history/AUDIT-CLOSURE-1.3.md`; он не подменяется итогами нового выпуска.

## Исправление 1: обход AST не должен менять литералы

В 1.3 `trim_alias` рекурсивно посещал любые словари. Литерал
`{op:"call",name:"alias",args:[]}` считался вызовом, хотя по грамматике
это пользовательские данные. После удаления forwarding alias менялся
возвращаемый результат; проверка типов эту подмену не обнаруживала.

В 1.4 обход начинается только в телах функций и следует
`language.expression_children`. Литералы и аннотации типов непрозрачны.
Меняется только имя настоящего выражения `call`; имена builtin/service
не переписываются. После преобразования проверяется весь AST.

Регрессии проверяют возвращаемые AST-подобные данные в record/list,
неизменность исходной программы и реальные вызовы внутри композиторов.
Равенство fuel не заявляется: удаление вызова меняет стоимость исполнения.

## Исправление 2: допустимая программа не должна портить снимок

В 1.3 программа глубины 31 проходила в wire-запросе глубины 32, но
`SessionSnapshot.programs[id]` помещал её ещё на один уровень глубже.
Следующий `cid(SessionSnapshot, snapshot)` отказывал с LIMIT.

В 1.4 снимок хранит каждую программу как ASCII-текст её канонических
байтов. Live Session продолжает исполнять AST. Restore сначала проверяет
внешний digest, затем декодирует программы, проверяет каноничность,
`check_agent` и соответствие каждого ключа содержимому.

Регрессии проверяют wire-глубину 31, прямую глубину 32, bootstrap,
prepare, evaluate, admit, training и восстановление. Дополнительно
проверены пять программ по 65536 байт и насыщенная история из четырёх
планов: 96 исполнений по 64 шага, 96 учебных записей и четыре решения.
Это конкретные граничные проверки, не механизированная теорема о
любом произвольном расширении Session или о ресурсах CPython.

## Отдельное изменение постановки: improve после полного успеха

Правило 1.3 требовало хотя бы одного перехода false→true. После полного
успеха родителя оно закономерно отвергало более дешёвого успешного
кандидата. Это ограничение прежней постановки, не нарушение её контракта.

В 1.4 Mission фиксирует `SUCCESS_THEN_PARETO_COST_1`. Успешный кандидат
может пройти improve по прежнему приросту успеха либо, если обе программы
успешны на всех уровнях, по строгому Парето-улучшению вектора:

- число действий на каждом уровне;
- число вычисленных VM-выражений на каждом уровне;
- размер канонической программы.

Ни одна координата не должна ухудшиться, хотя бы одна должна улучшиться.
Стоимость вычисляет evaluator при проверке записанного исполнения и
подписывает её в Assessment. ReleaseDecision сохраняет измерения и
результаты сравнения. Более дешёвый неуспех, нарушение родительского
контракта, выигрыш в среднем с потерей одного уровня и подделка стоимости
не проходят. Возрастание одной оси при уменьшении другой не проходит
именно этот профиль; нового взвешенного скаляра здесь нет.

Семантика retain сохранена: полный успех и наследованные гарантии, без
обязательного сохранения всех фактических затрат. VM fuel не измеряет
wall-clock latency, цену LLM, стоимость typecheck или evaluator. Для
неуспешного пути измерен только префикс; он не участвует в cost-ветке.

## Дополнения к спецификации

§14.1–14.4 задают требования к будущему адаптеру: лестница абстракции,
проверяемое противоречие, нормированная идеальность, защищённая история
verifier, прогноз и кредит оператору, структурное разнообразие и
область действия формулы допуска. Уже реализованные в 1.3 меры не
объявляются новыми исправлениями. §15.1 описывает mG-Pass@k по первичным
источникам и условия её применения; усреднённая метрика не заменяет
жёсткие инварианты. Эти расширения не выдаются за исполняемый TRIZ-агент,
скрытый holdout или готовый bandit.

## Совместимость и проверка

Версия 1.4 меняет формат снимка, схемы Mission/Assessment/ReleaseDecision,
домен content IDs и purpose для производных ключей. Старые снимки не
мигрируют автоматически. Начинается новая доверенная Session, старые
свидетельства не становятся свидетельствами нового выпуска.

`reports/verification.json` содержит фактическое число тестов, ошибок,
состояний K12, результаты wire-fuzz и проверку replay при разных
PYTHONHASHSEED. `reports/demo.json` показывает три последовательных
выпуска на всех 12 уровнях: paint → solver с noop → обычный solver →
формализованная политика. Второй переход проходит новый improve,
последний проходит retain; все 72 эпизода оплачены.

Контроль манифеста остаётся вычисляемой проверкой. Сборочный флаг
`--write-manifest` не используется при независимой проверке готового
архива. Документация защищается внешним хешем архива. Ни успешные тесты,
ни наличие хеша не означают отсутствия всех возможных дефектов.
